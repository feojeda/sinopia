# v1.4 Execution and Review Protocol

**Applies to**: all v1.4 implementation phases  
**Proposal**: `docs/PROPOSAL_v1.4_interactive_questions_agent_adapters.md`  
**Status**: Required for v1.4 phases

---

## Goal

Every v1.4 phase must be implemented with an isolated implementation subagent and reviewed before merge.

The review can be performed by:
- An external peer reviewer tool (Codex, Claude CLI, Gemini CLI, etc.)
- A dedicated reviewer subagent spawned by the implementing agent
- Skipping review entirely when explicitly approved by the user

The intent is to keep the implementation agent focused while making review independent, cheap, and recorded in the PR.

---

## Phase Execution Rules

For each phase:

1. Start from the default branch after the previous phase has merged.
2. Create the phase branch documented in that phase file.
3. The main implementing agent must create a dedicated implementation subagent for the phase.
4. The implementation subagent must work only on that phase's scope.
5. The implementation subagent must run the phase verification commands.
6. The implementation subagent must commit only that phase's changes.
7. The implementation subagent must push the branch and create a PR to the default branch.
8. After the PR exists, run peer review according to the configured review mode (see Review Configuration below).
9. The phase cannot be merged until the reviewer reports approval, or the user explicitly overrides with `skip-review`.
10. The next phase cannot start until the current PR is approved and merged.

Do not create an implementation subagent for the next phase while the current phase is still pending review or changes.

---

## Review Configuration

The review mode is controlled by `REVIEW_MODE` per phase or globally:

| Mode | Value | Behavior |
|------|-------|----------|
| External tool | `codex`, `claude`, `gemini`, etc. | Invoke an external CLI tool as peer reviewer |
| Subagent | `subagent` | Spawn a dedicated reviewer subagent within the current session |
| Skip | `skip` | No automated review; user accepts responsibility |

Default: `codex`.

The user can override the mode at any point by stating it explicitly (e.g. "use subagent reviewer for this phase" or "skip review").

## External Peer Reviewer Invocation

This section applies when `REVIEW_MODE` is set to an external tool (`codex`, `claude`, `gemini`, etc.).

### Codex

Run the reviewer from the repository root after the PR is created:

```bash
codex exec \
  -C "$PWD" \
  -c model_reasoning_effort='"low"' \
  "Peer review PR <PR_URL>. Leave actionable comments directly on the PR using gh. Focus on bugs, regressions, missing tests, and contract mismatches against the phase document. Do not implement fixes. Do not spawn subagents. At the end, output exactly one verdict line: APPROVED if no changes are needed, or NEEDS_CHANGES if fixes are required. Also state that your comments are in the PR."
```

### Claude CLI

```bash
claude --print \
  "Peer review PR <PR_URL>. Leave actionable comments directly on the PR using gh. Focus on bugs, regressions, missing tests, and contract mismatches against the phase document. Do not implement fixes. Do not spawn subagents. At the end, output exactly one verdict line: APPROVED or NEEDS_CHANGES."
```

### Gemini CLI

```bash
gemini -p \
  "Peer review PR <PR_URL>. Leave actionable comments directly on the PR using gh. Focus on bugs, regressions, missing tests, and contract mismatches against the phase document. Do not implement fixes. Do not spawn subagents. At the end, output exactly one verdict line: APPROVED or NEEDS_CHANGES."
```

If the local tool config already defaults to low reasoning effort, keep the explicit config override anyway so the intent is visible in logs.

The external reviewer must:

- Use `gh` to inspect the PR and leave comments in the PR.
- Run or inspect tests as needed.
- Output `APPROVED` only when the PR can merge as-is.
- Output `NEEDS_CHANGES` when any blocking or material issue remains.
- Not modify files.
- Not create subagents.
- Not implement the next phase.

If the reviewer cannot authenticate with GitHub or cannot leave comments, the phase is blocked until comments are posted by another review path.

## Reviewer Subagent Mode

This section applies when `REVIEW_MODE` is `subagent`.

The implementing agent must spawn a **dedicated reviewer subagent** with the following constraints:

1. The reviewer subagent must be a fresh context (no shared state with the implementation subagent).
2. The reviewer subagent must inspect the PR diff using `gh pr diff`.
3. The reviewer subagent must leave review comments on the PR using `gh`.
4. The reviewer subagent must output exactly one verdict: `APPROVED` or `NEEDS_CHANGES`.
5. The reviewer subagent must not modify any files in the working tree.
6. The reviewer subagent must not spawn further subagents.

The implementing agent should instruct the reviewer subagent with a prompt equivalent to:

```
You are a peer reviewer. Review PR <PR_URL>.
Use `gh pr diff` and `gh pr view` to inspect changes.
Leave inline comments via `gh api` for any issues found.
Focus on bugs, regressions, missing tests, and contract mismatches against the phase document.
Do not modify files. Do not spawn subagents.
At the end, output exactly one verdict line: APPROVED or NEEDS_CHANGES.
```

---

## Skip Review Mode

This section applies when `REVIEW_MODE` is `skip`.

When the user explicitly chooses to skip automated review:

- The implementing agent proceeds directly to the merge gate.
- The PR description must include: `Review: SKIPPED (user override)`.
- The user assumes full responsibility for unreviewed code.
- This mode should be used sparingly (e.g. trivial changes, hotfixes, or when the user will review manually).

---

## Merge Gate

The implementing agent may merge the PR only when all are true:

- The reviewer output includes `APPROVED` (or review was skipped with user override).
- The reviewer has left a summary comment on the PR (not required in skip mode).
- All required verification commands pass.
- The PR branch is up to date enough for the configured GitHub merge policy.
- There are no uncommitted phase changes.

If the reviewer outputs `NEEDS_CHANGES`, the implementation subagent must fix the issues in the same phase branch, push updates, and request review again using the same review mode.

---

## PR Description Requirements

Each PR description must include:

- Phase name and phase document path.
- Summary of implementation.
- Verification commands and results.
- Known limitations.
- Review mode used (`codex`, `claude`, `gemini`, `subagent`, or `skip`).
- Reviewer command or subagent prompt used.
- Final reviewer verdict (`APPROVED`, `NEEDS_CHANGES`, or `SKIPPED`).

---

## Cost Control

- Implementation subagents should use the cheapest acceptable model/profile for the phase unless the user explicitly authorizes otherwise.
- External peer reviewers must be invoked with low reasoning effort.
- Reviewer subagents should use the cheapest acceptable model/profile.
- Do not create additional reviewer subagents unless explicitly requested by the user or the review mode is `subagent`.
