# v1.5 Execution and Peer Review Protocol

**Applies to**: all v1.5 Gesso implementation phases  
**Proposal**: `docs/PROPOSAL_v1.5_gesso_lienzo_en_blanco_implementation_plan.md`  
**Roadmap**: `docs/ROADMAP_sinopia.md`  
**Status**: Required for v1.5 phases

---

## Goal

Every v1.5 phase must be implemented by a dedicated implementation subagent and reviewed by a separate peer-review subagent before merge.

The main coordinating agent is responsible for sequencing, but the implementation work and review work must be delegated:

- Implementation subagent: writes the code/docs/tests for one phase.
- Peer-review subagent: reviews the PR and leaves comments in the PR.
- Main coordinating agent: enforces gates, merges only after approval, then starts the next phase.

---

## Required Sequence

For each v1.5 phase:

1. Start from `main` after the previous phase has merged.
2. Create the phase branch documented in that phase file.
3. Spawn a dedicated implementation subagent for that phase.
4. The implementation subagent works only within the phase scope.
5. The implementation subagent runs all required verification commands.
6. The implementation subagent commits only that phase's changes.
7. The implementation subagent pushes the branch and creates a PR.
8. After the PR exists, spawn a separate peer-review subagent.
9. The peer-review subagent must inspect the PR and leave its comments directly in the PR.
10. If the review verdict is `NEEDS_CHANGES`, the implementation subagent fixes the issues, pushes updates, and the peer-review subagent reviews again.
11. Repeat implementation/review until the peer-review subagent returns `APPROVED`.
12. Only after `APPROVED`, merge the PR.
13. Only after the PR is merged, continue to the next v1.5 phase.

Do not begin a later v1.5 phase while an earlier v1.5 phase is unmerged.

---

## Implementation Subagent Requirements

The implementation subagent must:

- Read the phase implementation plan before editing.
- Read the v1.5 proposal and this protocol before editing.
- Keep changes within the phase scope.
- Use the repository's existing patterns before adding abstractions.
- Preserve legacy behavior unless the phase explicitly changes it.
- Add or update tests proportional to the phase risk.
- Run the verification commands listed in the phase plan.
- Produce a PR with the required description fields.
- Not merge its own PR.
- Not start the next phase.

The implementation subagent prompt should include:

```text
You are the implementation subagent for <PHASE_NAME>.
Read <PHASE_DOC>, docs/PROPOSAL_v1.5_gesso_lienzo_en_blanco_implementation_plan.md,
and docs/implementation_plans/v1.5_execution_review_protocol.md.
Implement only this phase. Preserve legacy behavior.
Run the required tests. Commit, push, and create a PR.
Do not merge. Do not start the next phase.
```

---

## Peer-Review Subagent Requirements

The peer-review subagent must:

- Use a fresh context separate from the implementation subagent.
- Inspect the PR with `gh pr view` and `gh pr diff`.
- Compare the implementation against the phase document, v1.5 proposal, and roadmap.
- Focus on bugs, regressions, missing tests, state-machine mistakes, CLI contract mismatches, installer/adapters breakage, and compatibility risks.
- Leave comments directly in the PR using GitHub review comments or PR comments.
- Not edit files.
- Not push commits.
- Not spawn additional subagents.
- Return exactly one final verdict line: `APPROVED` or `NEEDS_CHANGES`.

The peer-review subagent prompt should include:

```text
You are the peer-review subagent for PR <PR_URL>.
Use `gh pr view` and `gh pr diff` to inspect the PR.
Review against <PHASE_DOC>, docs/PROPOSAL_v1.5_gesso_lienzo_en_blanco_implementation_plan.md,
and docs/ROADMAP_sinopia.md.
Leave comments directly in the PR using `gh`.
Focus on bugs, regressions, missing tests, state-machine mistakes, CLI contract mismatches,
installer/adapters breakage, and compatibility risks.
Do not modify files. Do not push commits. Do not spawn subagents.
At the end, output exactly one verdict line: APPROVED or NEEDS_CHANGES.
```

If the peer-review subagent cannot leave comments in the PR because of authentication or tooling failure, the phase is blocked until a reviewer can post comments in the PR.

---

## Review Iteration Loop

When the peer-review subagent returns `NEEDS_CHANGES`:

1. The main coordinating agent sends the PR comments back to the implementation subagent.
2. The implementation subagent fixes the issues in the same phase branch.
3. The implementation subagent reruns required verification.
4. The implementation subagent pushes the updates.
5. The main coordinating agent requests another peer-review pass from a peer-review subagent.

This loop continues until the final peer-review verdict is `APPROVED`.

Do not merge with unresolved `NEEDS_CHANGES`.

---

## Merge Gate

A v1.5 phase PR may be merged only when all are true:

- The peer-review subagent returned `APPROVED`.
- The peer-review subagent left comments or a summary directly in the PR.
- Required verification commands pass.
- The PR description records verification results.
- The branch contains only the phase's intended changes.
- There are no uncommitted changes for the phase.

After merge, update local `main` before starting the next phase.

---

## PR Description Requirements

Every v1.5 PR must include:

- Phase name.
- Phase document path.
- Summary of changes.
- Files changed by category.
- Verification commands and results.
- Known limitations or deferred items.
- Implementation subagent identifier or description.
- Peer-review subagent prompt summary.
- Final peer-review verdict.
- Link or reference to PR comments left by the peer-review subagent.

---

## Prohibited Shortcuts

- Do not implement phases directly in the main coordinating agent.
- Do not review with the same subagent that implemented the phase.
- Do not merge before peer-review approval.
- Do not skip peer review unless the user gives explicit written override for that specific PR.
- Do not start the next phase before the current PR is merged.
- Do not broaden scope to Abbozzo, Studi, Opere, or Sinopia CLI migration during v1.5.
